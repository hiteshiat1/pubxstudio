# Manual actions for production publishing

This checklist covers actions that require the founder's provider accounts, billing decision, or permission to make a live post. It is not evidence that a channel is connected. Update each checkbox with a date and a nonsecret result or blocker. Never put client secrets, access/refresh tokens, authorization codes, passwords, database URLs, or screenshots containing them in GitHub or this file.

## 1. LinkedIn developer application — [issue #5](https://github.com/hiteshiat1/pubxstudio/issues/5)

- [ ] Sign in to [LinkedIn Developer Portal](https://www.linkedin.com/developers/apps), create or select an app controlled by you, and confirm the associated company page and app owner.
- [ ] In **Products** and **Auth**, check which products and scopes the app actually has. For member text posts, confirm `w_member_social`; for organization posts, confirm `w_organization_social` and any required organization discovery permissions. LinkedIn's [Posts API permissions](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api) and [OAuth guide](https://learn.microsoft.com/en-us/linkedin/shared/authentication/authorization-code-flow) are the references. Access depends on approved products; do not assume a requested scope is granted.
- [ ] Check whether the app also has `r_liteprofile` for `GET /v2/me`. The member publishing service uses that Profile API response's `id` to build the Posts API person URN. If approved, set server-only `PUBX_LINKEDIN_REQUEST_LITEPROFILE=1` and reconnect; if denied, record member publishing as blocked in issue #7. Do not substitute the OIDC `sub` without provider confirmation.
- [ ] Confirm which company pages the connecting member may publish for and their page role. Record page names and nonsecret page URNs only after the app can discover them. If organization access is denied, record it as blocked; member publishing may still proceed.
- [ ] Register the exact production callback `${PUBX_APP_ORIGIN}/api/social/linkedin/callback` in the app's **Auth** tab (and a separate exact staging URL if used). Set server-only `PUBX_LINKEDIN_CLIENT_ID` and `PUBX_LINKEDIN_CLIENT_SECRET` in the deployment secret manager. Confirm both Sign In with LinkedIn using OpenID Connect (`openid profile`) and member posting (`w_member_social`) products are approved. Then sign in as workspace founder and open `/api/social/linkedin/start?workspaceId=<your workspace UUID>`. Confirm the account appears as connected without sharing the code or token.
- [ ] Record the app name, nonsecret client ID, granted products/scopes, redirect URL host/path, page eligibility, and any review status in issue #5. Put the client secret only in the deployment secret manager.

## 1a. Workspace login app — [issue #14](https://github.com/hiteshiat1/pubxstudio/issues/14)

- [ ] In [GitHub OAuth Apps](https://github.com/settings/developers), register an OAuth app for PubxStudio. Set its callback URL to the exact production origin plus `/api/auth/github/callback`; add the staging callback separately if used. Disable wildcard callback matching. See [GitHub's setup guide](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app).
- [ ] Set server-side `PUBX_APP_ORIGIN`, `PUBX_GITHUB_CLIENT_ID`, `PUBX_GITHUB_CLIENT_SECRET`, and `PUBX_FOUNDER_GITHUB_ID`. The founder ID is the numeric GitHub account ID (not the login name); confirm it under your own account before configuring. Add `PUBX_INITIAL_WORKSPACE_NAME` if you want a different first workspace name. Keep the client secret in the deployment secret manager.
- [ ] Sign in from `/studio` using the founder account, confirm a founder workspace is created once, then use the authenticated member API to invite other GitHub IDs as `approver` or `operator`. Do not grant an unknown account a role. Record only nonsecret login and role-test evidence in issue #14.

## 2. X developer application and cost decision — [issue #10](https://github.com/hiteshiat1/pubxstudio/issues/10)

- [ ] Sign in to the [X Developer Portal](https://developer.x.com/) and confirm the project, app, and account that will own posts. Check the current write API availability, request limits, and pricing shown in your console. Prices and eligibility can change.
- [ ] Decide whether to enable any paid access. **Do not buy credits or accept a charge solely for this checklist.** Record an explicit approved budget or “no spend approved” in issue #10.
- [ ] In the app's user-authentication settings, enable OAuth 2.0 authorization code with PKCE and confirm the permissions needed for posting, identity lookup, and refresh if offered. Record the granted scopes by their exact names, not the requested names.
- [ ] After you explicitly approve any API spend, register the exact production callback `${PUBX_APP_ORIGIN}/api/social/x/callback` (and a separate exact staging URL if used). Set server-only `PUBX_X_CLIENT_ID` and `PUBX_X_CLIENT_SECRET` in the deployment secret manager. Confirm `tweet.read tweet.write users.read offline.access` are available, then sign in as founder and open `/api/social/x/start?workspaceId=<your workspace UUID>`. Confirm the connected profile without sharing codes or tokens.
- [ ] Record the nonsecret app/client ID, callback host/path, granted permissions, account handle, pricing/limit decision, and any access blocker in issue #10. Keep client secrets only in the deployment secret manager.

## 3. Hosting, secrets, and production acceptance — [issues #20](https://github.com/hiteshiat1/pubxstudio/issues/20) and [#21](https://github.com/hiteshiat1/pubxstudio/issues/21)

- [ ] Choose the production web, worker, and PostgreSQL hosting arrangement and approve any new spend before provisioning. Provide the public HTTPS origin and staging origin so exact OAuth redirects can be registered.
- [ ] Configure `DATABASE_URL`, `PUBX_CREDENTIAL_KEYS`, `PUBX_CREDENTIAL_ACTIVE_KEY_ID`, and provider app credentials in a managed server-side secret store. Follow [database setup](db/README.md); generate encryption keys locally and never paste them into chat or issues. Arrange backups and test a restore in staging.
- [ ] Keep `PUBX_PUBLISHING_ENABLED`, `PUBX_LINKEDIN_POSTING_ENABLED`, and `PUBX_X_POSTING_ENABLED` unset or `0` until each channel's app permissions, billing decision, and controlled live test are approved. Enable only the authorized provider flags in the worker's server-side environment. Every scheduled job still needs the founder's exact text/account/time confirmation in Studio before the worker can claim it.
- [ ] Review the exact proposed test post text, destination account/page, and time before authorizing **each** live LinkedIn or X post. A successful mock test does not count. Approve any X API charge separately.
- [ ] After a controlled live test, record only the real provider post ID/URL, timestamp, account, and outcome in issue #21. Remove the test post manually if desired after recording evidence. Mark a provider channel blocked if its permissions or billing do not allow the test.
- [ ] If a job becomes **uncertain**, do not schedule the same text again. Inspect the actual destination account/page and verify whether the provider created the post. For X threads, inspect the partial thread and identify the exact uncertain part. In the authenticated founder workspace, send `POST /api/workspaces/<workspace UUID>/jobs/<job UUID>/reconcile` with JSON `{"action":"confirmed_published","providerPostId":"<verified provider ID>","evidence":"<where and when you verified it>"}` if it exists, or `{"action":"confirmed_absent","evidence":"<how you verified no post exists>"}` only if absence is confirmed. LinkedIn IDs are `urn:li:share:...` or `urn:li:ugcPost:...`; X IDs are numeric. Use the same-origin Studio session. Record the nonsecret outcome in issue #17. A confirmed X thread part resumes only remaining parts; an uncertain part is never blindly replayed.

## Current state

The database schema, encrypted credential primitive, LinkedIn and X text-post adapters, GitHub-backed workspace sessions, approval workflow, account selection/draft UI, durable queue and guarded dispatch worker, and LinkedIn/X OAuth callbacks have been implemented. The login and provider developer apps still need founder configuration. The worker is **not deployed** and all posting flags default off. No live provider post has been verified. Do not treat a draft export or a mocked provider response as a live publication.
