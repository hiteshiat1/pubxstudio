# PostgreSQL schema (PUB-02)

This directory provides the persistent data foundation from the [PUB-01 audit](../design/pub-01-architecture-audit.md). It does not connect the existing editor or publish action to the database yet. Those paths remain unsafe for production publishing until the credential, roles, approval, and queue issues are implemented.

## Configure and migrate

Use PostgreSQL 13 or later. Set a server-only `DATABASE_URL` for a database role that can create tables, indexes, functions, and triggers in its schema. Do not use a browser-exposed environment variable. Back up the database before upgrades. Run migrations once during deployment, before starting web or worker processes:

```sh
DATABASE_URL='postgresql://user:password@host:5432/pubxstudio' npm run db:migrate
```

Migrations are numbered SQL files in `db/migrations/`. The runner records a SHA-256 checksum in `schema_migrations`, uses a PostgreSQL advisory lock to serialize concurrent deploys, and applies each file in a transaction. Re-running it is safe; changing or deleting an applied file fails. Make schema changes by adding a new numbered migration. There is no automatic rollback for destructive changes.

For local integration tests, set `PUBX_TEST_DATABASE_URL` to a disposable PostgreSQL database and run `npm run test:db`. Tests create and remove only a uniquely named test schema. Without this variable the test is skipped. The test verifies fresh install through migration 001, upgrade to 002, persistence after reconnect, repeat migration, cross-workspace foreign keys, idempotency uniqueness, published ID requirement, and revision immutability.

## Schema and limits

- `users`, `workspaces`, and `memberships` identify tenants and actors. The workspace access service enforces roles and object-level reads. Routes use server sessions from migration 004; production login requires GitHub OAuth app configuration in [manual actions](../MANUAL_ACTIONS.md).
- `social_accounts` stores provider identity and encrypted credential metadata; it does not store raw tokens.
- Migration 003 replaces `credential_ref` with AES-256-GCM encrypted credential bytes, a key ID, expiry, and revocation metadata. `db/credentials.mjs` is an internal server-only primitive; it requires a founder membership before storing, reading, revoking, or rotating an account credential.
- Migration 006 adds one-use LinkedIn authorization state tied to a founder session and workspace. `src/server/linkedin-oauth.mjs` starts and completes the server-side exchange; `src/app/api/social/linkedin/{start,callback}/route.js` expose the browser redirects. Set server-only `PUBX_LINKEDIN_CLIENT_ID` and `PUBX_LINKEDIN_CLIENT_SECRET`, and register `${PUBX_APP_ORIGIN}/api/social/linkedin/callback` exactly in LinkedIn's developer portal. Start at `/api/social/linkedin/start?workspaceId=<workspace UUID>` while signed in as a founder. The flow requests `openid profile w_member_social`; the app must have both LinkedIn OIDC and member-posting products approved. LinkedIn's `userinfo.sub` identifies the connected member. No organization permission is requested here.
- Migration 007 adds one-use X OAuth state and a server-held PKCE verifier. `src/server/x-oauth.mjs` starts the confidential-client authorization flow, exchanges the code using Basic authentication, resolves `/2/users/me`, encrypts the user access/refresh tokens, and refreshes only when a refresh token was actually granted. Set server-only `PUBX_X_CLIENT_ID` and `PUBX_X_CLIENT_SECRET`; register `${PUBX_APP_ORIGIN}/api/social/x/callback` exactly in the X developer console. Start at `/api/social/x/start?workspaceId=<workspace UUID>` while signed in as founder. The flow requests `tweet.read tweet.write users.read offline.access`; access and billing remain subject to the founder's explicit decision in [manual actions](../MANUAL_ACTIONS.md). The founder may POST to `/api/workspaces/<workspace UUID>/accounts/<account UUID>/refresh` with same-origin credentials to rotate a granted X refresh token. No client secret or token is returned to the browser.
- Migration 008 records each X thread part, its content digest, reply parent, confirmed provider ID, and uncertain/failed status. `src/server/x-posts.mjs` validates X's weighted text length with the official `twitter-text` parser and sends a real `POST /2/tweets` when invoked by a trusted worker. `src/server/x-thread.mjs` accepts a single plain-text revision or a JSON revision of the form `{"posts":["first","reply",...]}` (up to 25 parts). The exact revision is approved before scheduling. It persists each part as `sending` before the provider call, then stores confirmed IDs. A confirmed prefix is never reposted; an uncertain part blocks further sending until manual reconciliation. The production dispatch worker and paid/live acceptance are separate work.
- Migration 009 records granted scope names only when the OAuth token response actually includes them. The authenticated `/api/workspaces/<workspace UUID>/accounts` API returns provider identity, scope names, status, and expiry without credential bytes. Founders may disconnect an account with same-origin `DELETE /api/workspaces/<workspace UUID>/accounts/<account UUID>`. Studio provides connect/reconnect, explicit publish-as selection, and a draft/approval form bound to that selected account; scheduling remains a separate action.
- `src/server/linkedin-member.mjs` resolves the current member's Profile API `id` from the same access token before constructing a person URN. It holds the approval, item, account, and job rows during the preflight and provider call. The OAuth flow requests `r_liteprofile` only when server-only `PUBX_LINKEDIN_REQUEST_LITEPROFILE=1`; enable it only after LinkedIn grants that permission. If the Profile API call is unavailable, member dispatch fails without calling the Posts API. The OIDC `sub` is never assumed to be the Posts API person ID. A founder-approved live test is still required.
- `content_items` and `content_revisions` store drafts and immutable revision bodies. The content service computes SHA-256 on insertion and verifies it before approval; migration 002 prevents update/delete of revision rows.
- `approvals` bind a revision, account, and actor. Migration 005 adds immutable approval events and a unique active approval per revision/account. Editing a draft revokes older approvals and cancels pending jobs. `publish_jobs` bind to the exact approval/revision/account tuple; `publish_attempts` require a provider post ID for published status. `db/queue.mjs` schedules only current approved revisions to connected accounts, atomically claims due work with leases, and marks expired leases uncertain. The authenticated jobs API lists UTC schedule times; Studio displays them in the viewer's local timezone. Provider dispatch, retry policy, and reconciliation are separate work.
- Composite foreign keys constrain related rows to the same workspace. Application queries still need workspace filters and authenticated authorization; SQL constraints alone do not prevent a privileged database connection from reading another workspace.
- No media object storage or key management is configured here. Browser ZIP export is separate from these tables. The unscoped server filesystem save action has been removed.

For backup and restore, use your managed PostgreSQL service's snapshot/restore mechanism or `pg_dump --format=custom` and `pg_restore` with a maintenance window. Restore into a separate database first, run `npm run db:migrate`, and verify `schema_migrations` and record counts before switching traffic. Do not put database URLs or dumps in Git.

## Credential key configuration (PUB-03)

Provision `PUBX_CREDENTIAL_KEYS` as a server-only JSON object mapping key IDs to random 32-byte base64 keys, and set `PUBX_CREDENTIAL_ACTIVE_KEY_ID` to the ID used for new encryption. Keep the key material in a managed secret store outside Git, browser code, and logs. The encryption binds ciphertext to its workspace and account ID. Example shape: `{"v1":"<base64-encoded-32-byte-key>"}`. Generate a key with `openssl rand -base64 32`; never paste the resulting value into an issue or PR.

To rotate keys, add a new key to the map, change the active ID, run `rotateKey` for each account through a trusted server maintenance path, verify all rows use the new ID, then remove the old key. Replacing a provider access/refresh token uses `store`; `revoke` clears encrypted bytes and marks the account revoked. Expired access tokens are rejected and marked expired. LinkedIn may issue refresh tokens only to eligible applications; the OAuth callback encrypts one when present but does not attempt programmatic refresh. Reconnect through the same authorization route when the access token expires.

There is deliberately no browser route to store or reveal tokens: the LinkedIn callback stores them server-side. The legacy publish action now fails closed, and the editor deletes previously stored social tokens from `localStorage` on load. Existing browser tokens must be reconnected through OAuth; they are not migrated into the database. LLM provider API keys still use browser storage and direct provider calls; moving those keys is outside this social credential issue and needs a separate security design.
