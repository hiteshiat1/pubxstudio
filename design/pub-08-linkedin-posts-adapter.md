# PUB-08: LinkedIn Posts API adapter

Checked 20 November 2026 against the official [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api) and [migration status](https://learn.microsoft.com/en-us/linkedin/marketing/integrations/migrations). The documented text post endpoint is `POST https://api.linkedin.com/rest/posts`; required headers include `Linkedin-Version` (`YYYYMM`) and `X-Restli-Protocol-Version: 2.0.0`. A successful create returns HTTP 201 and `x-restli-id` with a post URN. Version `202611` is active in the migration table, and is the adapter default. Set server-only `PUBX_LINKEDIN_API_VERSION` to another supported `YYYYMM` version when needed. Recheck provider support at deployment time.

`src/server/linkedin-posts.mjs` implements text-only creation. It accepts an already authorized member or organization URN, an access token supplied by a trusted server workflow, and reviewed text. It returns only a validated provider post ID. It does not discover authors, inspect organization roles, initiate OAuth, check revision approval, or persist a job. Those checks belong to PUB-05, PUB-06, PUB-07, PUB-14, and PUB-15 before any call to this adapter is allowed. The existing UI publish action remains disabled.

The adapter never calls the legacy `ugcPosts` endpoint. A 401/403 is normalized as authorization failure, 429 as rate limited, and ordinary 4xx as provider rejection. Network errors, 5xx, unexpected successful status, and 201 without a valid ID are marked `OUTCOME_UNCERTAIN`: the caller must reconcile before retrying because a post may have been created. Provider message bodies and tokens are never included in thrown errors or logs. It does not synthesize a URL or success ID.

Run `npm run test:linkedin` for mocked contract tests. These verify request path, method, headers, body, version override, accepted provider IDs, denial and rate-limit handling, uncertain outcomes, and invalid inputs. They do **not** prove access to a real LinkedIn app or a live post. A controlled live test requires founder approval and provider setup in later issues.
